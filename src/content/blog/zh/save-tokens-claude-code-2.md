## 习惯三：别打断缓存

上篇说过，长会话还用得起，全靠缓存。但它比你想象的更容易被打断。

服务端判断能不能用缓存，看的是这次请求的开头和上次是否一字不差。一样的部分按便宜的价格重读，只有新增的结尾需要完整处理。可开头只要有一处变了，从那儿往后的全部内容都要重新算（[来源](https://code.claude.com/docs/en/prompt-caching)）。

可以把它想成一摞叠好的盘子。往最上面再放一个很轻松；要换掉底下某一个，上面的就得全部拿下来重新摞。下面这几个操作，就是在动底下的盘子。

### 会打断缓存的操作

| 操作 | 后果 | 怎么避免 |
| --- | --- | --- |
| 中途切换模型 | 整段历史不走缓存重读一遍 | 开头选好，简单问题另开会话 |
| 中途调整思考强度 | 多数模型上同样会重读，部分新模型不受影响 | 开头选好 |
| 压缩对话 | 历史被摘要替换，对话部分的缓存重建 | 在任务之间的停顿处做 |
| 离开太久 | 缓存过期，回来的第一条消息重新处理全部上下文 | 离开前收尾，回来开新会话 |

表中内容来自 Claude Code 官方文档。

前三种是你主动做的，知道了就好避免。最后一种最隐蔽。缓存有有效期，默认五分钟或一小时，看你的计费方式：订阅用户在套餐额度内，主对话的缓存能保留一小时；按量付费的是五分钟（[来源](https://code.claude.com/docs/en/prompt-caching)）。也就是说，你去开个会、吃个饭，回来接着问的那一句，很可能是整个会话里最贵的一句。要离开一阵的话，先让它写好交接文档，回来直接开新会话。

### 两个常见的误会

也有两件事很多人以为会打断缓存，其实不会。

一是中途改 CLAUDE.md。它不会打断缓存，但改动也不会马上生效：Claude Code 在会话开始时读一次 CLAUDE.md，之后一直用那个版本，要等下次 `/clear`、`/compact` 或重启才重新加载（[来源](https://code.claude.com/docs/en/prompt-caching)）。刚改完说明书，AI 却好像“不听话”，多半是它还没读到新版本。

二是回退对话。用 `/rewind` 退回到之前某一轮，用的正是已经缓存过的那段开头，不需要重建。所以发现走错了路，回退比压缩划算。

这套“按开头匹配”的规则不是 Claude Code 独有的，各家模型服务的缓存基本都这么工作。总之，会话开始之后，少动开头的东西。

## 习惯四：少走弯路

前面三个习惯省的都是正常干活时的开销。真正的大头，往往是做错之后的返工。来回纠正五轮花掉的 token，比一开始多写三句话多得多，还搭上你的耐心。

### 一次把话说清楚

AI 不会读心。你给的信息越模糊，它越得自己去翻、去猜，每翻一次都在往上下文里塞东西。

OpenAI 给 Codex 用户总结过一个很实用的格式，一条好的任务描述包含四样东西：

- **目标**：要改什么，要做成什么样
- **相关上下文**：涉及哪些文件、文档、报错信息
- **约束**：要遵守的规范和架构，哪些东西不能碰
- **完成标准**：什么情况算做完，比如测试全部通过、某个 bug 不再出现

比如“登录有问题，帮我看看”，它得先满项目找登录相关的代码，再猜你说的“问题”是什么。换成“auth.ts 的登录函数在密码为空时不报错，加上校验，现有测试要全部通过”，它可以直接打开那个文件开干，也知道什么时候算做完。

### 复杂的活，先出计划

复杂的任务别急着让它动手。先让它调查、出方案，你看过点头了，再写代码。

方向错了，在计划阶段发现，损失几千 token；等代码写完才发现，就是整段推倒重来。在 Claude Code 里按 Shift+Tab 就能切到计划模式。

### 看到不对，立刻喊停

很多人习惯让 AI 先做完，再说“不对，重来”。可错误的那一大段已经留在上下文里了，之后每一轮都得背着，还可能继续干扰它的判断。

一看到它往错的方向走，就按 Esc 打断，然后用 `/rewind`（或者连按两次 Esc），把对话和代码一起退回到出错之前的检查点（[来源](https://code.claude.com/docs/en/costs)）。错误的那一段就从上下文里彻底消失了。

### 让它能自己检查

在任务里附上测试用例、预期输出或者一张截图，让它知道“对”长什么样。它能自己验证，问题就会在交到你手上之前被发现，省掉一轮“你看这里不对”的来回。

### 让它少说两句

还有个小细节：输出比输入贵。可以要求它只改需要改的地方，别把整个文件重写一遍；回答直接给结论，别先复述你的问题。这类要求写进 CLAUDE.md，就不用每次交代。

这些在 Codex 里同样适用，它的计划模式用 `/plan` 或 Shift+Tab 打开。

## 习惯五：把脏活交给子代理

这个习惯要用得巧，用不好反而更费钱。

### 子代理为什么能省

有些活不难，但过程特别啰嗦：跑一遍测试、查一份文档、翻几千行日志、在几十个文件里找一个函数的定义。你真正要的只是结论，比如“第 42 行的测试挂了，原因是空指针”。可要是让主对话自己做，翻过的每个文件、跑出的每一行输出，都会留在上下文里。

子代理就是干这个的：它在自己独立的上下文里查，查完只把结论交回来，过程全留在它那边（[来源](https://code.claude.com/docs/en/costs)）。主对话因此保持干净，之后每一轮都更便宜，AI 也更专注。

### 但它不是免费的

子代理自己发出的请求照样算你的用量。而且它从零开始，读不到主对话的缓存，得自己重新建一份（[来源](https://code.claude.com/docs/en/prompt-caching)）。

值不值得派出去，看这个活的过程是不是又长又没用。几千行日志、几十个文件，值得派；只读一两个小文件，直接在主对话里做反而更省。

### 两个省钱的用法

- **给子代理配小模型**。查找、整理这种简单的活，可以在子代理的配置里指定用 Haiku。
- **别一次开太多**。官方给过一个数字：多个代理组成团队协作时，在计划模式下的用量大约是普通会话的 7 倍（[来源](https://code.claude.com/docs/en/costs)）。

Codex 也有类似的子代理功能，建议同样是把探索、测试、排查这类边界清楚的活交出去，让主线程专心处理核心问题。

## 别省过头

看到这儿，你可能想把所有会话都切得碎碎的、所有活都扔给最小的模型。别急。

要压低的是做完一件事的总花费，不是单条消息用了多少 token。只盯着后者，很容易两头亏：

- **信息给得太少**。为了省几百 token 不说清背景，结果它做错了，重来一遍花掉几万。
- **模型选得太小**。小模型反复改不对，三轮下来比大模型一次做对还贵，还搭进去你的时间。
- **会话切得太碎**。还是同一个问题，就留在原会话里，前面的推理线索还用得上。OpenAI 的说法是一个会话对应一个完整的工作单元，真正该避免的是把整个项目塞进一个会话。
- **什么都派给子代理**。小活派出去，启动成本比活本身还高。

有个简单的自检办法：如果你发现自己在反复纠正它，问题多半不是 token 用多了，而是前面省过头了。

## 一张检查清单

五个习惯不必全记住。我按开工前、进行中、收工时整理成了一张清单，贴在手边就行。

**开工前**

- 这是新话题吗？是的话开新会话
- 模型和思考强度选好了吗？选好就别中途换
- 任务描述里有目标、相关文件、约束、完成标准吗
- 任务复杂吗？复杂就先让它出计划

**进行中**

- 它走偏了吗？立刻打断并回退，不要等它做完
- 要查大量资料或跑长输出的命令吗？交给子代理
- 要贴日志吗？先筛出有用的几行
- 要离开一阵吗？离开前让它写 handover 文档

**收工时**

- 任务告一段落了吗？清空，或者在这个停顿处压缩
- 看一眼 `/usage`：缓存命中率正常吗，什么东西占得最多
- 同一个错误它犯了两次吗？把教训写进项目说明书

## 换个工具怎么对应

| 概念 | Claude Code | Codex |
| --- | --- | --- |
| 项目说明书 | CLAUDE.md | AGENTS.md |
| 看用量和上下文 | `/usage`、`/context` | `/status` |
| 压缩历史 | `/compact` | `/compact` |
| 找回旧会话 | `/resume` | `/resume` |
| 先计划再动手 | Shift+Tab 进入计划模式 | `/plan` 或 Shift+Tab |
| 长任务接力 | handover 文档 | PLANS.md 执行计划 |

Codex 一列来自 OpenAI 的官方最佳实践（[来源](https://developers.openai.com/codex/learn/best-practices)）。

## 写在最后

回到开头那个周三下午。现在回头看，那天的错几乎都能在这两篇里找到对应：一个会话从周二拖到周三，隔了一晚缓存早就过期；中途插进部署这种不相干的话题；看不懂报错，就把整份日志贴进去。

这些习惯没有一个是复杂的技巧，大多是“换个话题就开新会话”“说清楚再动手”这样的常识。难的是干活正投入的时候想起它们。希望这两篇能帮你早一点想起来。
