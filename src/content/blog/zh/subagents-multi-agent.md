适合已经会用 Claude Code 做完整功能、想让它同时干几件事的人。建议先读 10（子代理省 token 的部分）和 11（计划模式和回退）。

10 里讲子代理，角度是省 token：把啰嗦的活派出去，主对话保持干净。这篇不再重复那部分，换个问题：子代理和多 Agent 到底能帮你做成什么，代价是什么，什么时候该用、什么时候别用。

先说结论。Claude Code 官方最佳实践里有一句话我觉得最关键：把同一件事交给子代理，默认还是同一个模型（或者更小的）在做，你得到的是并行或者一双新的眼睛，不是更聪明的答案。

下面所有的判断，基本都从这句话出发。

## 先分清几个层级

“多 Agent”这个词现在用得很乱。在 Claude Code 里，从轻到重大概是这么几层：

| 形式 | 是什么 | 结果去哪 |
| --- | --- | --- |
| 子代理 | 主对话派出去的帮手，有自己的上下文 | 干完交一份结果给主对话 |
| 分叉（fork） | 一种特殊的子代理，继承主对话的全部历史 | 同上 |
| Agent 团队 | 多个独立的 Claude Code 实例，一个当组长 | 成员之间直接发消息，共用任务列表 |
| 多个并行会话 | 你自己开几个会话，各干各的 | 你自己汇总 |

日常用得最多的是前两种。Agent 团队目前还是实验功能，默认关闭。最后一种不算功能，是一种用法，但很实用，后面会讲。

## 子代理：大部分时候它自己会用

### 内置的三个

Claude Code 自带几个子代理，你不用配置，它会根据情况自己派：

- **Explore**：只读，专门在代码库里搜索和分析。你问“这个项目里哪儿处理了登录”，它多半就会派 Explore 去翻。
- **Plan**：只读，在计划模式下帮主对话做调研。11 里讲过。
- **general-purpose**：什么工具都能用，处理既要调查又要动手的多步任务。

Explore 和 Plan 启动时不加载你的 CLAUDE.md，为的是快、便宜。这一点有时候会让人困惑：你在 CLAUDE.md 里写了某条规矩，Explore 却好像不知道。它确实没读到。

### 分叉：带着全部记忆出去干活

普通子代理是从零开始的，你给它什么，它就知道什么。分叉不一样，它继承主对话到目前为止的全部内容，然后在后台干一件事，干完把结果交回来。

它的好处是不用重新交代背景。另一个好处在缓存上：分叉的系统提示和工具定义跟主对话一模一样，第一次请求就能复用主对话的缓存，所以对于需要同样背景的任务，它比新开一个子代理便宜。

你可以自己用 `/subtask` 开一个，比如：

```text
/subtask 给目前改过的解析器代码补单元测试
```

它在后台跑，你在主对话里接着干别的。现在的版本里分叉模式默认是开的，Claude 也会自己决定什么时候分叉。

## 什么时候值得派出去

官方文档列了四种情况，我按自己的理解说一下：

**一是能并行的独立活。** 比如要同时调研认证、数据库、接口三个模块，三件事互不依赖，派三个子代理同时查，总时间短很多。前提是真的互不依赖。如果 B 要等 A 的结论，并行就没意义。

**二是输出很长、你只要结论的活。** 跑一遍完整测试、搜整个仓库、翻一份长日志。这就是 10 里讲的那种情况。

**三是需要一双没看过过程的眼睛。** 这是我觉得最被低估的用法。主对话写了半天代码，它对自己的思路是“认同”的，让它自己检查，很容易看不出问题。派一个没看过写代码过程的子代理去审，效果会好很多。官方的 `/code-review` 就是这个思路，在一个全新的子代理里审当前的改动。

**四是要限制权限的活。** 比如审查员只能读、不能改。这个限制是 Claude Code 强制执行的，不是在提示词里“请求”它别改。

反过来，这几种情况留在主对话里更好：

- 需要你频繁来回确认、反复调整的
- 计划、实现、测试几个阶段共用大量背景的
- 改一两行的小改动
- 赶时间的。一个新的子代理得先自己摸清背景，有时候反而比你在主对话里直接做还慢

还有一种情况连子代理都不用：只是想就当前对话里的内容问个小问题，用 `/btw`。它不调用工具，回答也不会加进对话历史。

## 自己写一个子代理

内置的不够用，可以自己写。子代理就是一个带 YAML 头的 Markdown 文件，放在 `.claude/agents/`（只对当前项目生效）或者 `~/.claude/agents/`（对你所有项目生效）。

最值得先写的是一个只读的审查员。官方文档里给的例子差不多是这样：

```markdown
---
name: reviewer
description: 对照需求文档审查改过的文件。实现完一个功能、提交之前使用。
tools: Read, Grep, Glob
---
你在审查一份不是你写的代码。把改过的文件和给你的需求文档对比，
确认每条需求都实现了，列出的边界情况都有测试，
只报告影响正确性的问题，不管代码风格。
```

几个要点：

- `tools` 只给 `Read, Grep, Glob`，它就改不了任何文件
- 最后那句“不管代码风格”别省。官方特意提醒过，让一个审查员去找问题，它总能找出点什么，你要是每条都改，最后会多出一堆没必要的抽象层和测试
- 简单的活可以加一行 `model: haiku`，便宜很多

写好之后，可以直接让 Claude 用它：“用 reviewer 对照 SPEC.md 审一下这次的改动”。结果回到主对话，主对话接着修。这正好接上 11 里那套流程的最后一步。

也可以不自己写文件，直接告诉 Claude 你要什么样的子代理、存到哪儿，让它写。写完打开文件看一眼头部的配置对不对就行。

## 花多少钱

子代理的每一次请求都算你的用量。10 里说过它读不到主对话的缓存（分叉除外），而且子代理的缓存默认只有 5 分钟。

省钱的办法官方给了几条，加上我自己的理解：

- 简单的活配 Haiku
- 让它交回简短的摘要。派二十个子代理，每个交回一大段，主对话照样会被撑满
- 用 `/usage` 看每类子代理占了多少用量，判断哪个值得留
- 注意后台的活。子代理在你没打字的时候也在发请求

Claude Code 默认最多同时跑 20 个子代理，子代理还能再派子代理，默认最多往下三层。这些上限是防失控的，不是让你用满的。

## Agent 团队：先确认真的需要

Agent 团队是另一回事。它启动几个完全独立的 Claude Code 实例，一个当组长分配任务、汇总结果，成员之间可以直接发消息，还共用一个任务列表。

它目前是实验功能，要在设置里加环境变量 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` 才能打开，官方也写明了在恢复会话、任务协调、退出这些地方还有已知问题。

官方建议的适用场景是：

- 几个成员从不同方向调研同一个问题，然后互相质疑
- 新模块，各成员负责互不干扰的部分
- 调试时有几种互相竞争的假设，各自去验证
- 跨前端、后端、测试的改动，每层一个人负责

代价也写得很清楚：成员在计划模式下运行时，团队的 token 用量大约是普通会话的 7 倍。顺序执行的任务、改同一个文件的任务、依赖很多的任务，用单个会话或子代理更合适。

Anthropic 工程博客讲他们的多 Agent 研究系统时，给过一组更直观的数字：在他们的数据里，单个 agent 的 token 用量大约是普通聊天的 4 倍，多 Agent 系统大约是 15 倍。同一篇文章里，多 Agent 版本在他们内部的研究评测上比单 Agent 好了 90.2%。两个数字放在一起看：多 Agent 确实能做成单 Agent 做不成的事，但只有任务本身值这个钱时才划算。

## 更朴素的并行：自己开几个会话

很多时候你要的并行，其实不需要任何高级功能：开两个终端，各跑一个 Claude Code，各干一件事。

唯一要注意的是别让它们改同一份代码。官方的做法是用 git worktree，每个会话一个独立的工作目录：

```bash
claude -w feature-search
```

这会在一个新的 worktree 里启动会话。新的 worktree 是一份全新的签出，`.env` 这类被 git 忽略的文件不会自动带过去，依赖也没装。需要的话可以在仓库根目录放一个 `.worktreeinclude`，列出要复制过去的文件，比如 `.env`。

第二个会话还有个现成的用处：当审查员。一个会话写代码，另一个会话去读写好的文件，它没看过写的过程，你把它找到的问题贴回第一个会话。这是最便宜、最好理解的“多 Agent 协作”，你自己就是那个传话的组长。

## 一张判断表

| 你的情况 | 建议 |
| --- | --- |
| 改一两行，或者要频繁来回确认 | 主对话里直接做 |
| 只想就当前内容问个小问题 | `/btw` |
| 要跑长输出的命令、搜大范围的代码 | 子代理，配小模型 |
| 后台补测试、写文档，需要当前背景 | 分叉（`/subtask`） |
| 想要一次独立的审查 | 只读的审查子代理，或 `/code-review` |
| 几件真正独立的事，想同时推进 | 多个会话加 worktree，或者并行子代理 |
| 几个方向要互相讨论、互相质疑 | 才考虑 Agent 团队，先看清用量 |
