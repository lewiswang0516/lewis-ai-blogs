适合已经用 Claude Code 写过几个小功能、开始被返工折腾的人。建议先读 [09、10 两篇](/zh/blog/save-tokens-claude-code-1/)省 token 的文章，这篇会直接用到里面讲过的上下文和缓存。

10 里我提过一句：真正贵的往往不是正常干活，而是做错之后的返工。那篇讲的是返工怎么费 token，这篇换个角度，讲怎么用 Claude Code 自带的三样东西把返工压下来：计划模式、检查点、回退。

这三样单独看都很简单，按一个键或者敲一条命令的事。真正有用的是把它们串成一个固定的流程：动手之前先对齐方向，动手之后随时能退，退完了知道下一步怎么改。

## 先把“完成”说清楚

在讲计划模式之前，先说一件更靠前的事：你自己得知道要什么。

很多返工不是 AI 做错了，而是一开始就没说清楚。你脑子里想的是“加个搜索框，能按标题和标签搜”，嘴上说的是“加个搜索”。它按字面做了一个只搜标题的版本，你看了说不对，它再改，来回几轮，才拼出你本来想要的东西。

如果自己也没想好，可以反过来让它问你。Claude Code 官方最佳实践里推荐过一个做法，直接这么说：

```text
我想给博客加站内搜索，但细节还没想清楚。你来问我问题，问到你能写出需求文档为止，然后写进 SPEC.md。
```

它会一条一条地问：搜哪些字段，要不要支持中文分词，搜索结果怎么排，放在哪个页面。你回答完，它把结论写成一份 SPEC.md。

接下来有个小细节：写完 SPEC.md 之后，开一个新会话再动手。前面那一长串问答对写代码没什么用，留在上下文里只会每轮都多带一截。新会话第一句话就是“按 SPEC.md 做”，干净，而且有一份写下来的完成标准。这份文件后面检查的时候还用得上。

## 计划模式：先看方案，再让它动手

### 它做什么，不做什么

计划模式下，Claude 会读文件、跑一些查看类的命令去摸清楚项目，然后写出一份方案，但不会改你的源码。你批准之前，所有编辑都被拦着。

进入的方式有三种：

- 会话里按 Shift+Tab，在几种权限模式之间切换，直到底部状态栏显示 `⏸ plan mode on`
- 在某一条消息前面加 `/plan`，比如 `/plan 给文章页加上一篇、下一篇的导航`
- 启动时直接带参数：`claude --permission-mode plan`

方案写好后，它会问你怎么继续。大致是三个选项：批准并让它自动接着干，批准但每一处修改都要你点头，或者不批准、继续改方案。还可以按 Ctrl+G，把方案在你自己的编辑器里打开，直接改几行再交回去。

这一步的成本很低。按官方文档的说法，计划阶段需要摸清代码时，会交给一个只读的研究子代理（Plan）去翻，翻文件的过程留在它那边，不进主对话。方向错了，在这里发现，损失的是一份方案；等代码写完才发现，就是一堆要撤销的修改。

### 一份方案该看什么

我看方案主要看四样东西：

- **改哪些文件**。列出来的文件和我预想的对不上，多半是它理解错了需求，或者它找到了我不知道的依赖。两种情况都值得停下来问一句。
- **按什么顺序改**。先改数据结构还是先改页面，先写测试还是先写实现。顺序不对，中间某一步就会跑不起来。
- **怎么验证**。方案里没写怎么确认做对了，我会补一句“做完跑 `npm run build`，再打开预览页确认”。
- **不碰什么**。比如“不要改现有的 URL 结构”“不要引入新依赖”。这类约束最好在方案阶段就写进去，不然它可能顺手“优化”了。

看到哪一点不对，选“继续改方案”，直接说哪里要改。别批准之后再在执行过程中纠正，那时候它已经按错的方案改了一半文件。

### 什么时候不用

不是每件事都要先出方案。如果你能一句话说清楚这次要改什么，就直接让它做。改个错别字、调一下按钮颜色、给函数加一个参数，这类事情走计划模式反而多一轮来回。

我自己的判断标准是：会动到三个以上文件，或者我自己也说不清具体怎么实现的，就先出方案。

## 检查点：每一条消息之前都有一个存档

### 它是怎么存的

Claude Code 会在你每发一条开启新一轮的消息之前，自动记下当时代码的状态，这就是检查点。不用手动开，也不用手动存。

几个具体的规则：

- 一个会话里保留最近 100 个检查点的文件快照
- 检查点跟着会话一起保存，`/resume` 回到旧会话之后照样能回退
- 快照默认大约 30 天后清理，想保留更久可以改 `cleanupPeriodDays` 设置

### 它管不到的地方

这部分很多人没注意，出了事才发现回退不干净：

- **命令行改的文件**。检查点只跟踪 Claude 用自己的编辑工具改过的文件。如果某个文件只被 `rm`、`mv` 或者某个脚本动过，回退不会把它恢复。
- **子代理改的文件**。大部分情况下，子代理的修改不进你的检查点，回退时只恢复主对话里改过的那些文件。
- **你自己手动改的、或者另一个会话改的**。不在跟踪范围里。
- **软链接和硬链接**。回退时会跳过，并提示跳过了几个文件。

所以官方的说法是：检查点是会话级别的快速撤销，不是版本控制。真正要留的东西，还是交给 git。我的习惯是每完成一个能跑起来的小段落就 commit 一次，检查点用来管两次 commit 之间的事。

## 回退：发现走偏，退回去重来

### 怎么回退

输入 `/rewind`，或者在输入框为空的时候连按两次 Esc，会弹出一个列表，列着这个会话里你发过的每一条消息。选中一条，可以做这几件事：

- **代码和对话一起恢复**：两样都退回到那条消息之前
- **只恢复对话**：对话退回去，代码保持现在的样子
- **只恢复代码**：代码退回去，对话保留
- **从这里开始压缩**：把这条之后的对话压成一段摘要
- **压缩到这里为止**：把这条之前的对话压成摘要，后面的保留

退回之后，你当时发的那条消息会重新出现在输入框里。这一点很好用：你可以把它改得更准确，再发一次。

### 回退和纠正，选哪个

它做错了，有两种处理方式。一种是接着说“不对，应该是……”，另一种是退回去，把原来那条消息改好重发。

我现在基本都选后者。原因在 09、10 里讲过：错误的那段过程会一直留在上下文里，之后每一轮都要带着，还会干扰它的判断。回退能把它彻底拿掉，而且回退用的是已经缓存过的开头，不用重建缓存。

官方最佳实践里还有一条更具体的建议：同一件事纠正了两次还不对，就别纠正第三次了。直接 `/clear` 开新会话，把前两次学到的东西写进一条新的、更清楚的指令里。第三次纠正只是在一个已经有两次失败尝试的对话里继续加东西。

### 先试大胆的方案

有了回退，试错的成本就很低了。

比如一个页面加载慢，有个保守方案（加缓存）和一个激进方案（换一种渲染方式）。以前我会先试保守的，因为激进的改坏了不好收拾。现在可以先让它试激进的，跑一下看效果，不行就回退，再试保守的。

如果两个方案都想留着对比，可以用 `/branch`。它会把当前对话复制一份，你切到新的分支里试另一个方向，原来的会话原样保留，用 `/resume` 随时能回去。

## 让它自己知道做没做完

回退解决的是“走偏了怎么办”。还有一类返工是它以为做完了，其实没有。

最直接的办法是给它一个能跑、结果只有通过和不通过的检查：测试、构建、类型检查、lint，都行。官方文档说，如果项目里已经有这样的命令，CLAUDE.md 里最有用的一行就是写上怎么跑它。

在指令里可以这么写：

```text
改完跑 npm run build，有报错就继续修，直到构建通过。把你最后跑的命令和输出贴给我。
```

最后一句很重要。只说一句“全部通过了”说明不了什么，让它把命令和输出贴出来，你扫一眼就知道是真是假。

如果想更强制一点，还有两个办法，这里只点一下，14 篇讲自动化时会细说：

- `/goal`：设一个完成条件，比如“tests 目录下的测试全部通过”，每一轮结束时由另一个模型判断是否达成，没达成就让它接着干
- Stop hook：每次 Claude 想结束这一轮时，自动跑你指定的检查命令，没通过就把错误信息退回给它

## 串起来：一次完整的流程

拿“给博客加站内搜索”举例，按这篇的流程走一遍：

1. 新会话，让它问问题，写出 SPEC.md
2. 开新会话，进计划模式，让它按 SPEC.md 出方案
3. 看方案：改哪些文件、什么顺序、怎么验证、不碰什么。不对就继续改方案
4. 批准，让它动手，并要求每一步做完都跑构建
5. 盯住前一两分钟。一旦看到它往奇怪的方向走，按 Esc 打断
6. 走偏了就 `/rewind`，把那条指令改准确再发；同一个问题纠正两次还不行，就 `/clear` 重来
7. 做完一个能跑的段落，commit 一次
8. 全部做完，开一个子代理对照 SPEC.md 检查一遍（下一篇会讲怎么做）

## Codex 里怎么对应

Codex 也有计划模式，用 `/plan` 或 Shift+Tab 打开，用法和这里差不多。检查点和回退的具体机制两边不一样，我没在 Codex 上系统地对比过，就不展开了，用之前建议看一眼它的官方文档。不管用哪个工具，用 git 兜底都是对的。
